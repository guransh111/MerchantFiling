# 14. What data, what method, and what real data exists

## Part 1: Which dataset is used?

### The main dataset is synthetic (simulated), and calibrated to real Indian data

The 1,000 merchants and ~3 million UPI payments in the demo are **generated by our own program**
(`src/generate.py`). This is a deliberate choice, not a shortcut:

1. **Real transaction-level UPI data is not public.** Individual payments are personal data, protected
   by bank secrecy and the DPDP Act. No payment company or NPCI publishes them.
2. **Real data has no answer key.** Even a payment company doesn't know which of its merchants are
   betting fronts it hasn't caught yet. In a simulation we *plant* the fronts, so we can measure
   exactly how many the system finds and how many honest shops it bothers.

### What's real inside the simulation

| Part | Real source |
|---|---|
| **Average payment size per category** | **NPCI's official UPI statistics, July 2025** (`data/real/`). Simulated averages match within 1%: kirana ₹214, restaurants ₹158, pharmacies ₹398, electronics ₹1,093, sweet shops ~₹262 |
| How betting fronts behave | Enforcement Directorate cases (1xBet, Parimatch), the CUTS International report on UPI mules, The Ken / mFilterIt reporting: round deposits, match-time spikes, payers across India, quick payouts, rented accounts, shared devices |
| Cricket calendar | IPL dates (late March to May) and match times (7:30pm, weekend 3:30pm double-headers) |
| Diwali | Actual date (8 Nov 2026) and the category-specific rush (sweets, electronics) |
| Cities, states, tiers | Real Indian cities in tiers 1 to 3 |

### What's invented (assumptions you should be able to defend)

| Assumption | Value | Why it's reasonable |
|---|---|---|
| Share of fronts / rented / honest drifters | 4% / 1% / 3% | Illustrative; the Generate page lets you change it |
| Hours of trade per category | e.g. kirana busy 7–10am and 5–9pm | Common sense; check against a real shop's data |
| Bet sizes | ₹100 to ₹10,000, mostly ₹500 / ₹1,000 | Typical deposit menus on betting sites |
| How hard fraudsters hide | 30% evasion by default | Stress-tested from 0% to 100% |

### The reality check

Before calibration, our simulated restaurants averaged ₹503 per payment; real NPCI data says
₹113–158. Electronics was ₹3,750 vs a real ₹1,093. We fixed this using the real figures, re-ran
everything, and **the headline results didn't change**: 100% of bad merchants caught, 0 of 920 honest
shops penalised, and Diwali alerts at 62% vs 1%. A few secondary numbers moved slightly (e.g. 12 instead of 10
honest-but-changed merchants are asked a question). The method doesn't depend on our ticket-size guesses.
`reports/results.md` section 10 shows the check.

## Part 2: How are the decisions made?

Seven steps, all explainable:

| Step | Method | In plain words |
|---|---|---|
| 1. Signals | Weekly aggregation | 10 numbers per merchant per week (match-hour share, night share, round amounts, out-of-state payers, repeat payments, amount variety, same-day pass-through, payout accounts, growth, size vs declared) |
| 2. Drift score | **Robust z-scores vs a peer group**, capped and summed, squashed to 0–100 | "How far is this merchant from similar shops in the same week, on several measures at once?" Medians and MAD are used so a few fraudsters can't distort "normal" |
| 3. Network | **Personalized PageRank** on a graph of shared phones, bank accounts, customers, payout accounts; **Louvain** clusters | "Is it tied to known betting accounts?" |
| 4. Change point | **Least-squares single change-point** on the weekly score | "Which week did it change, and did a phone/bank change happen then?" |
| 5. Learning loop | **Logistic regression** on analysts' confirm/clear decisions, out-of-fold | "What do confirmed cases have in common?" Suggests weights; never acts alone |
| 6. Anomaly | **Isolation Forest** | "What's unusual that we have no rule for?" Picks audits only |
| 7. Decision | **Rule-based ladder** with thresholds, corroboration and fairness rules | Monitor → Ask → Friction → Review (needs network evidence) → Offboard (needs a human) |

**Risk score = drift score + 0.25 × network score** (a known-bad match sets it to at least 95).
Thresholds: Ask at 60, Friction at 75, Review at 90. These can be tuned in the dashboard, or set by the
cost tool in rupees.

**Why mostly rules and statistics, not a big ML model?** There are no labels on day one, every action
must be explainable to the merchant and the regulator, and peer comparison works without training data.
Machine learning (the learning loop) is layered on top as labels accumulate.

## Part 3: Real data you can use

| Data | Real? | Level | Where | How to use it here |
|---|---|---|---|---|
| **NPCI UPI ecosystem statistics** (by merchant category, P2P vs P2M) | Real | Monthly totals | npci.org.in → UPI → Ecosystem Statistics | Already used for calibration (July 2025). Download newer months and update `data/real/` |
| **RBI payment system indicators** | Real | Monthly totals | rbi.org.in | Context for the problem slide |
| **Your organisation's own merchant data** | Real | Transaction level | A payment company, a bank, or a case-competition sponsor | Upload directly (file 12). **This is the only route to real transaction-level testing** |
| Berka / PKDD'99 Czech bank dataset | Real (anonymised, 1990s) | Transaction level | Public mirrors (e.g. GitHub `ldaniel/R_Bank_Berka`) | Bank accounts, not merchants; only useful to test that uploads work at scale |
| Sparkov credit-card fraud dataset | Synthetic | Transaction level, with merchant and category | Kaggle `kartik2112/fraud-detection` | Uploadable (merchant → merchant_id, category → category, cc_num → payer, trans_date_trans_time → ts, amt → amount). Its fraud labels are *card* fraud, not merchant misuse, so treat it as a format test |
| PaySim mobile-money dataset | Synthetic (based on real logs) | Transaction level | Kaggle | Has merchant recipients; same caveat |

**Bottom line for judges:** there is no public, real, transaction-level dataset of UPI merchants
with known betting fronts, and there can't be, for privacy reasons. So we built a simulation calibrated
to real NPCI category data and real enforcement cases, measured the method on it, stress-tested it,
and made it accept a payment company's real data with no code changes.

### Note on how the real figures were collected

NPCI's website blocks automated access from cloud servers, so the July 2025 figures were taken from
reputable reports that reproduce NPCI's release (Business Standard, SBI Research, OfficeChai, The Head
and Tale). Sources and confidence levels are in `data/real/README.md`. If you can open NPCI's page
yourself, please check the numbers against the original.
